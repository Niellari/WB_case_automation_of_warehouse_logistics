# WB Case: Автоматизация складской логистики

## Обзор проекта

**Задача:** Кейс Wildberries — автоматизация складской логистики. Нужно спрогнозировать количество отгруженных ёмкостей (`target_2h`) по маршрутам за 2-часовые окна и спроектировать систему автоматического вызова транспорта.

Проект включает **две части:**
1. **Предсказательная модель** (ML) — предсказание `target_2h`
2. **Прототип системы** (веб-сервис) — архитектура, бизнес-логика, вызов транспорта

---

## Данные

| | Train | Test |
|---|---|---|
| **Размер** | 4 342 000 строк, 12 колонок | 10 000 строк, 3 колонки |
| **Период** | 01.03.2025 — 30.05.2025 10:30 | 30.05.2025 11:00 — 15:30 |
| **Маршруты** | 1000 | подмножество |
| **Склады** | 53 | — |

- В тесте **нет status_1–8** и target — нужно предсказать target_2h
- Данные с шагом 30 минут (~4342 точки на маршрут за 3 месяца)
- Целевая переменная: mean=68.7, median=48, max=1517, 0 встречается

---

## Текущее решение — train_model.py

**Модель:** LightGBM (regression, MAE)

**Фичи (29 штук):**
- Временные: hour, minute, dow, day, week, is_weekend, slot
- Идентификаторы: office_from_id, route_id (как числа)
- Агрегаты из train: средние/медианы/std по route, route+hour, route+dow, route+dow+hour, office, office+hour
- Лаговые: lag_1..lag_8, lag_mean_4, lag_mean_8

**Валидация:** holdout — последние 4.5 часа train

**Параметры LightGBM:** lr=0.05, num_leaves=127, early_stopping=50, до 2000 деревьев

---

## Ключевые наблюдения и проблемы

### Сильные стороны:
- Грамотная структура: агрегаты пересчитываются на train-split (без утечки)
- Лаговые фичи захватывают недавнюю активность маршрута
- Clipping предсказаний >= 0

### Слабости и потенциал улучшения:

1. **Status-фичи не используются** — в train есть 8 колонок status_1–8 с данными о прохождении товаров через этапы обработки. Они доступны в train, но **не в test**, поэтому их нельзя использовать напрямую. Однако можно использовать их для создания исторических агрегатов (средние статусы по маршруту/часу).

2. **route_id и office_from_id как числа** — используются как числовые фичи, а не категориальные. LightGBM поддерживает категориальные через `categorical_feature`.

3. **Валидация слабая** — holdout всего 4.5 часа (10 точек). Лучше использовать несколько дней или TimeSeriesSplit.

4. **Лаги для теста берутся из конца train** — ОК для теста (он сразу после train), но get_lag_features итерирует по строкам (`iterrows`) — крайне медленно на 4.3М строк.

5. **Метрика** — модель обучается на MAE, но соревновательная метрика WAPE + |Relative Bias|. Можно попробовать кастомную loss-функцию.

6. **Нет системной части** — задание требует веб-сервис, архитектуру, бизнес-метрики, README. Этого пока нет.

---

## Метрика соревнования

```
Score = WAPE + |Relative Bias|
WAPE = Σ|y - ŷ| / Σy
RBias = |Σŷ / Σy - 1|
```
